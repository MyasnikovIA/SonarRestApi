# Как собрать `session.txt` и что с ним делать

Собрать данные для `session.txt` несложно: это фактически «слепок» авторизованного запроса из вашего браузера к SonarQube. Поскольку в основе `SessionParser` лежит разбор HTTP-заголовков, вам нужно извлечь из DevTools браузера `Host`, `Cookie` и `X-XSRF-TOKEN`.

---

## 0. Что важно знать сразу

- **`session.txt` создаётся автоматически** при первом запуске сервера — с шаблоном-инструкцией внутри. Сервер без сессии работает, но data-эндпоинты отвечают `503 Session Not Ready`.
- **После сохранения сессии** (через файл, PUT-запрос, web или консоль) **автоматически запускается пересбор снимка в фоне** — данные становятся доступны через несколько минут (зависит от размера проекта). Следите через `GET /api/status` или `GET /api/health`.
- **При истечении cookie** (`JWT-SESSION` протух) все data-эндпоинты начнут отвечать `401 Unauthorized`. Лечение — заново извлечь cookie (шаги ниже) и применить одним из способов (раздел 5).
- **Файл — это полный доступ к аккаунту**. Не коммитьте в Git, не показывайте `session show` на записи экрана, см. раздел 8.

---

## 1. 🔍 Открыть DevTools и найти запрос

1. Войдите в SonarQube в вашем браузере.
2. Откройте **Инструменты разработчика** (обычно `F12` или `Ctrl+Shift+I` / `Cmd+Option+I`).
3. Перейдите на вкладку **Network** (Сеть).
4. **Обновите страницу** (F5), чтобы DevTools начал записывать трафик.
5. Найдите любой успешный запрос к API SonarQube. Например, в списке запросов можно отфильтровать по `Fetch/XHR` и найти что-то вроде `api/issues/search` или `api/project_analyses/search`. Убедитесь, что у запроса статус `200`.

---

## 2. 📋 Извлечь нужные заголовки

Самый надёжный способ — посмотреть заголовки запроса. Поскольку `SessionParser` умеет читать как формат `Key: Value`, так и пары строк, вы можете просто скопировать нужные значения.

### Способ А (через вкладку Headers)

1. Кликните на выбранный запрос в списке Network.
2. На панели справа откроются детали. Найдите раздел **Request Headers** (Заголовки запроса).
3. Вам нужны значения следующих заголовков:
   * **`Host`**: домен вашего SonarQube (например, `sonar.example.com`);
   * **`Cookie`**: самая важная часть. Скопируйте **всё значение** целиком. Там будут, как минимум, `XSRF-TOKEN` и `JWT-SESSION`;
   * **`X-XSRF-TOKEN`**: если этот заголовок присутствует (SonarQube часто его требует для POST-запросов), скопируйте его значение. Если его нет — `SessionParser` попробует извлечь токен из cookie `XSRF-TOKEN`.

### Способ Б (через "Copy as cURL" — быстрее)

1. Кликните правой кнопкой мыши по выбранному запросу в списке Network.
2. Выберите **Copy** → **Copy as cURL**.
3. Вставьте скопированную команду в любой текстовый редактор. В ней будут все нужные заголовки (`-H 'Cookie: ...'`, `-H 'X-XSRF-TOKEN: ...'`). Оттуда их легко скопировать.

---

## 3. 📝 Сформировать `session.txt`

`SessionParser` поддерживает два формата, но формат `Key: Value` — самый простой и понятный.

### Формат `Key: Value` (рекомендуется)

```text
Host: sonar.example.com
Cookie: XSRF-TOKEN=abc123def456...; JWT-SESSION=eyJhbGciOiJIUzI1NiJ9...
X-XSRF-TOKEN: abc123def456...
```

*Если у вас нет отдельного заголовка `X-XSRF-TOKEN`, эта строка не обязательна. Парсер найдёт токен в `Cookie`.*

### Альтернативный формат (пары строк)

Если вы копировали заголовки построчно, можно использовать и его. Парсер поймёт, что это пары, если не найдёт `Host` в формате `Key: Value`.

```text
Host
sonar.example.com
Cookie
XSRF-TOKEN=abc123def456...; JWT-SESSION=eyJhbGciOiJIUzI1NiJ9...
X-XSRF-TOKEN
abc123def456...
```

> 💡 **Проверка валидности до отправки.** Парсер требует наличия `Host` и `Cookie`. Если одного из них нет, ответ будет `400 Невалидный формат сессии: В дампе нет заголовка Host / Cookie`.

## 4. 🚀 Применить сессию — 4 способа

Все 4 способа работают одинаково: сохраняют `session.txt`, перезагружают `SonarClient`, запускают пересбор снимка в фоне.

### 4.1. Найти `session.txt` рядом с JAR и отредактировать вручную

Если запускали сервер без `--session=`, по умолчанию ищется `session.txt` в текущем каталоге.

```bash
# 1. Открыть в редакторе
nano session.txt

# 2. Вставить содержимое (раздел 3)

# 3. Через консоль (если она запущена):
session reload
# или через REST:
curl -X POST 'http://127.0.0.1:6060/api/session/reload?build=true'
```

### 4.2. Через web-интерфейс

1. Открыть `http://localhost:6060/`.
2. Перейти на вкладку **Сессия (Session)**.
3. Вставить текст сессии в textarea.
4. Нажать **Save session (PUT /api/session)**.

Ответ покажет `host`, `hasCookie`, `buildStarted: true` — снимок пересобирается в фоне.

### 4.3. Через REST API (PUT)

**Самый удобный способ для CI/CD:**

```bash
curl -X PUT 'http://127.0.0.1:6060/api/session?project=MY_PROJECT&build=true' \
     --data-binary @session.txt
```

**Ответ:**
```json
{
  "saved": true,
  "path": "session.txt",
  "host": "sonar.example.com",
  "xsrf": "abc...",
  "hasCookie": true,
  "buildStarted": true,
  "buildProject": "MY_PROJECT",
  "note": "Пересбор снимка идёт в фоне, прогресс: GET /api/status"
}
```

**Особенности:**
- Тело запроса — **сырой текст** сессии. Сервер сам валидирует и пишет на диск.
- Если дамп битый — файл **не перезапишется**, старая рабочая сессия останется. Получите `400` с описанием ошибки.
- `build=false` — не запускать пересбор (например, если хотите собрать снимок вручную позже).

### 4.4. Через консоль (stdin процесса)

```
sonar:MY_PROJECT> session set /path/to/session.txt
[console] session updated from /path/to/session.txt
          host = sonar.example.com
[console] snapshot rebuild started in background
```

Пригодится, когда сессия лежит в отдельном файле `new_session.txt`.

### 4.5. Проверка, что всё применилось

```bash
# 1) сессия загружена?
curl -s http://127.0.0.1:6060/api/health | jq '.sessionReady'
# → true

# 2) как идёт пересбор?
curl -s http://127.0.0.1:6060/api/status | jq '.snapshot'
# → { "status": "BUILDING", "phase": "resolving_rules", "progress": 150, "progressTotal": 342, ... }

# 3) когда готово?
curl -s http://127.0.0.1:6060/api/status | jq '.snapshot.status'
# → "READY"
```

Или через консоль:

```
sonar:MY_PROJECT> status
snapshot:
  status   = READY
  issues   = 342
  ...
```

## 5. 🔄 Что делать, когда сессия протухла

Признаки:
- `/api/health` → `"sessionReady": true`, но data-эндпоинты отвечают `401 Unauthorized`;
- в логах — `SessionExpiredException`;
- в web-интерфейсе — ошибки «Unauthorized» на всех вкладках;
- при `auto` (AI-обработка) — автостоп с сообщением «СЕССИЯ SONARQUBE ИСТЕКЛА (HTTP 401)».

### Что делать

1. **Заново получить cookie** (шаги 1–3). Не пытайтесь «продлить» старую — она уже невалидна.
2. **Применить новую сессию** — любым из 4 способов (раздел 4).
3. **Пересобрать снимок** — автоматически запустится после PUT/reload, либо вручную:
   ```
   sonar:MY_PROJECT> refresh wait
   ```
   Или через API:
   ```bash
   curl -X POST 'http://127.0.0.1:6060/api/refresh?project=MY_PROJECT&wait=true'
   ```
4. **Если прервалась `auto`** — её можно **продолжить** с того же места:
   ```
   sonar:MY_PROJECT> auto HIGH SECURITY --yes
   ```
   Уже обработанные issues не подхватятся (они больше не `OPEN`), будут взяты только оставшиеся.

## 6. 🕒 Срок жизни cookie

`JWT-SESSION` имеет ограниченный срок действия (обычно настраивается в SonarQube — от нескольких часов до суток). По истечении:

- все `GET /api/*` начинают возвращать `401 Unauthorized`;
- в web-интерфейсе появляется индикатор ошибки;
- в консоли — ошибки при любых командах, которые ходят в Sonar.

**Автоматического «обновления» cookie нет** — это ограничение SonarQube, не приложения. Придётся повторить шаги 1–4.

> 💡 **Совет:** если проект большой и `auto` идёт долго (часы), сессия может истечь прямо по ходу. Приложение обрабатывает это корректно — останавливает `auto`, печатает блок «СЕССИЯ ИСТЕКЛА» с инструкцией, сохраняет `failed keys`. После обновления cookie — просто повторить `auto` с теми же параметрами.

## 7. 🧰 Все способы управления сессией — сводка

| Что нужно | Как сделать |
|---|---|
| Прочитать текущую сессию (raw) | `GET /api/session` · консоль: `session show` · web: вкладка «Сессия» |
| Заменить сессию (сырой текст) | `PUT /api/session` · web: «Save session» · консоль: `session set <path>` |
| Перечитать с диска | `POST /api/session/reload` · консоль: `session reload` |
| Сохранить текущую сессию в файл | консоль: `session save <path>` |
| Проверить, что применилась | `GET /api/health` · консоль: `health` / `status` |
| Дождаться пересбора снимка | `GET /api/status` (опрос) · консоль: `status` / `refresh wait` |
| Принудительно пересобрать | `POST /api/refresh?wait=true` · консоль: `refresh wait` |

**Автоматический пересбор после `PUT /api/session` или `POST /api/session/reload`:**
- Параметр `build=true` (по умолчанию) — пересбор запускается в фоне.
- `build=false` — не запускать (пригодится, если хотите отредактировать session.txt, но не пересобирать снимок сразу).

## 8. ⚠️ Важные нюансы и безопасность

### HttpOnly cookie

В некоторых конфигурациях SonarQube cookie `XSRF-TOKEN` может быть помечена как `HttpOnly`. Это значит, что JavaScript не может её прочитать, но вы **всё равно увидите её** в DevTools на вкладке Network (DevTools показывает все заголовки). Инструкция выше работает в любом случае.

### Срок жизни

`JWT-SESSION` имеет ограниченный срок действия (обычно настраивается в SonarQube). Если сервер начнёт возвращать ошибки `401 Unauthorized` или `403 Forbidden`, скорее всего, сессия истекла — повторите шаги 1–4, чтобы получить свежие cookie.

### Безопасность файла

- `session.txt` — **полный доступ** к вашему аккаунту в SonarQube (в виде cookie сессии).
- **Никогда** не передавайте его третьим лицам.
- **Не коммитьте** в Git — добавьте `session.txt` в `.gitignore`.
- **Не оставляйте** в местах с общим доступом (public S3, shared disk, etc.).
- `GET /api/session` вашего же REST API отдаёт содержимое в открытом виде — учитывайте это при reverse-proxy и настройке firewall.
- `session show` в консоли тоже печатает cookie/XSRF в терминал — не запускайте при записи экрана / в общем терминале.
- Если сервер запущен с `-Dsonar.api.token=SECRET`, доступ к `/api/session` требует `Authorization: Bearer SECRET` — это частично снимает риск.

### Что делать, если сессия попала в чужие руки

1. Немедленно **разлогиньте все сессии** в SonarQube (Profile → Security → Log out of all devices). Это инвалидирует все cookie, включая украденную.
2. Замените `session.txt` (или удалите — сервер начнёт работать без сессии).
3. Проверьте, не было ли подозрительных действий (логи SonarQube → Administration → System → Web Server Logs).

## 9. 📂 Где хранится `session.txt`

По умолчанию — рядом с `SonarRestApi-*.jar` (в текущем каталоге). Порядок поиска:

1. `--session=<path>` в параметрах запуска;
2. `session.txt` в текущем каталоге (CWD).

Если файла нет — сервер **не падает**, работает без сессии:
- `GET /api/health` → `"sessionReady": false`;
- data-эндпоинты → `503 Session Not Ready`;
- web-интерфейс откроется, но покажет «session not ready» в шапке.

**Создание при первом запуске:** `BootstrapFiles` автоматически создаёт `session.txt` с шаблоном-инструкцией внутри (все строки начинаются с `#`, парсер их пропустит). Просто откройте файл и вставьте сессию.

**Несколько окружений** (dev / staging / prod):

```bash
# dev
java -jar app.jar --session=/opt/sonar/dev-session.txt --project=PROJ-DEV

# prod
java -jar app.jar --session=/opt/sonar/prod-session.txt --project=PROJ-PROD
```

Файлы независимы.
